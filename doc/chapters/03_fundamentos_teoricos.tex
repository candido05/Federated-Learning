\section{FUNDAMENTOS TEÓRICOS}

Este capítulo apresenta os conceitos fundamentais que sustentam o desenvolvimento deste trabalho. A primeira parte descreve o Aprendizado Federado: como funciona, sua base matemática e as estratégias de combinação de modelos avaliadas. A segunda parte apresenta os três algoritmos de boosting --- XGBoost, LightGBM e CatBoost --- com ênfase nas características que os tornam adequados para dados financeiros. A terceira parte apresenta o framework Flower, utilizado para implementar e simular o ambiente federado.

\subsection{Aprendizado Federado}

\subsubsection{Definição e Características}

O Aprendizado Federado é uma forma de treinar modelos de aprendizado de máquina em que os dados permanecem nos dispositivos ou servidores de cada participante e nunca são centralizados \cite{mcmahan2017fedavg}. Em vez de enviar os dados para um servidor central, cada participante treina o modelo localmente com seus próprios dados e envia apenas o modelo resultante --- nunca os dados brutos --- para ser combinado com os modelos dos outros participantes. Este processo se repete por várias rodadas de comunicação (\textit{rounds}) até que o modelo global alcance um desempenho satisfatório \cite{yang2019fl}.

Essa abordagem surgiu como resposta às preocupações com privacidade de dados e às regulamentações como o GDPR \cite{gdpr2016} e a LGPD, que restringem a centralização de informações pessoais. Ela também resolve um problema prático: transferir grandes volumes de dados entre instituições é caro, lento e, em muitos casos, proibido por lei \cite{konecny2016communication}.

O ciclo de treinamento federado segue cinco etapas encadeadas. Cada etapa é resultado da anterior, formando um processo contínuo de aprendizado colaborativo onde os dados jamais abandonam os dispositivos dos participantes.

\begin{figure}[H]
\centering
\includegraphics[width=0.55\textwidth]{figures/fl-initialize-global-model.png}
\caption{Etapa 1: Inicialização do modelo global no servidor central. Fonte: \cite{flower2024whatisfl}}
\label{fig:fl_initialize_fund}
\end{figure}

\textbf{Etapa 1 --- Inicialização:} Tudo começa no servidor. Antes que qualquer participante entre em cena, o servidor cria o modelo global inicial --- um modelo ainda sem experiência, partindo de uma configuração neutra. Esse ponto de partida comum é fundamental: garante que todos os participantes, independentemente de quem são ou de quais dados possuem, comecem a partir do mesmo lugar.

\begin{figure}[H]
\centering
\includegraphics[width=0.60\textwidth]{figures/fl-send-global-model.png}
\caption{Etapa 2: Distribuição do modelo global para os participantes. Fonte: \cite{flower2024whatisfl}}
\label{fig:fl_send_model_fund}
\end{figure}

\textbf{Etapa 2 --- Distribuição:} Com o modelo criado, o servidor o envia para os participantes selecionados naquela rodada. Antes da transmissão, o modelo é convertido para uma sequência de bytes (\textit{serialização}), tornando-o compatível com qualquer tipo de rede ou sistema. É importante notar o que \emph{não} acontece aqui: nenhum dado é transferido. Os dados de cada participante permanecem intactos em seus próprios dispositivos, aguardando a próxima etapa.

\begin{figure}[H]
\centering
\includegraphics[width=0.60\textwidth]{figures/fl-local-training.png}
\caption{Etapa 3: Treinamento local nos participantes com dados privados. Fonte: \cite{flower2024whatisfl}}
\label{fig:fl_local_training_fund}
\end{figure}

\textbf{Etapa 3 --- Treinamento local:} É aqui que o aprendizado de fato acontece. Cada participante treina o modelo recebido usando apenas seus próprios dados privados, sem compartilhá-los com ninguém. O modelo se adapta às características particulares de cada participante --- às fraudes que aquele banco específico já viu, às transações que aquela instituição processa. A privacidade não é uma promessa: é uma consequência direta da arquitetura. Sem dados saindo do dispositivo, não há nada para ser interceptado \cite{mcmahan2017fedavg}.

\begin{figure}[H]
\centering
\includegraphics[width=0.60\textwidth]{figures/fl-send-model-updates.png}
\caption{Etapa 4: Envio dos modelos atualizados para o servidor. Fonte: \cite{flower2024whatisfl}}
\label{fig:fl_send_updates_fund}
\end{figure}

\textbf{Etapa 4 --- Envio das atualizações:} Após o treinamento, cada participante devolve ao servidor apenas o modelo atualizado --- nunca os dados que usou para treiná-lo. O que é transmitido são os padrões aprendidos, não os registros originais. Esta etapa representa o principal custo de comunicação do ciclo \cite{konecny2016communication}: quanto mais participantes e maior o modelo, mais largura de banda é necessária. Por isso, estratégias de compressão e seleção de participantes são áreas ativas de pesquisa no campo.

\begin{figure}[H]
\centering
\includegraphics[width=0.55\textwidth]{figures/fl-aggregate-model-updates.png}
\caption{Etapa 5: Combinação dos modelos no servidor para gerar o novo modelo global. Fonte: \cite{flower2024whatisfl}}
\label{fig:fl_aggregate_fund}
\end{figure}

\textbf{Etapa 5 --- Agregação:} O servidor recebe todos os modelos atualizados e os combina para produzir um novo modelo global. Esse modelo é, em essência, uma síntese do que cada participante aprendeu com seus dados locais: ele carrega o conhecimento de todos sem que ninguém tenha revelado seus dados. Ao final desta etapa, o ciclo reinicia --- o novo modelo global é distribuído novamente e o processo se repete por várias rodadas (\textit{rounds}) até que o desempenho global seja satisfatório \cite{yang2019fl}.

\paragraph{Formulação matemática}

O objetivo formal do Aprendizado Federado é encontrar o modelo global $w$ que minimize a perda média ponderada entre todos os participantes:

\begin{equation}
\min_{w} F(w) = \sum_{i=1}^{N} \frac{n_i}{n} F_i(w)
\end{equation}

onde $F_i(w)$ é a perda local do participante $i$, $n_i$ é o número de amostras desse participante e $n$ é o total de amostras de todos os participantes. Em termos simples: o modelo global tenta ser o melhor possível para todos os participantes ao mesmo tempo, dando mais peso a quem tem mais dados.

As principais características que diferenciam o Aprendizado Federado do treinamento centralizado são:

\textbf{Privacidade:} Os dados nunca saem dos participantes. Apenas os modelos atualizados são transmitidos.

\textbf{Comunicação reduzida:} Transmite-se apenas o modelo, não os dados completos, o que é muito mais eficiente em termos de largura de banda \cite{konecny2016communication}.

\textbf{Dados heterogêneos (Non-IID):} Cada participante pode ter dados com distribuições muito diferentes dos demais, o que é um dos principais desafios do Aprendizado Federado \cite{zhu2021noniid}.

\textbf{Desequilíbrio entre participantes:} O número de amostras pode variar muito. Estratégias de combinação ponderada evitam que participantes com mais dados dominem o modelo global \cite{chai2024survey}.

\textbf{Diversidade de dispositivos:} Os participantes podem ter capacidade computacional e de rede muito diferentes, exigindo estratégias adaptativas \cite{bonawitz2019scale}.


\subsubsection{Estratégias de Combinação de Modelos}

As estratégias de combinação definem como os modelos locais são unidos para gerar o modelo global. A escolha da estratégia afeta diretamente a velocidade de estabilização (\textit{convergência}), a qualidade do modelo final e o volume de dados transmitidos. Neste trabalho são exploradas duas estratégias específicas para modelos de boosting \cite{flower2020}.

\textbf{Estratégia Bagging}

Na estratégia de Bagging, todos os participantes treinam seus modelos em paralelo a partir de um mesmo ponto de partida e enviam os resultados para o servidor. O servidor combina os modelos recebidos calculando a média das probabilidades preditas por cada um:

\begin{equation}
\hat{y}_{global}(x) = \frac{1}{|\mathcal{S}|} \sum_{i \in \mathcal{S}} M_i(x)
\end{equation}

A partir da segunda rodada, o melhor modelo da rodada anterior é enviado a todos os participantes como ponto de partida (treinamento incremental, ou \textit{warm start}), permitindo que o conhecimento acumulado seja preservado. Esta estratégia é inspirada no método clássico de agregação por reamostragem (\textit{Bootstrap Aggregating}), adaptado para o ambiente federado onde os dados já estão naturalmente divididos entre os participantes \cite{liu2020fedforest}.

\textbf{Estratégia Cíclica (\textit{Cyclic})}

Na estratégia Cíclica, os participantes treinam em sequência, um de cada vez. Em cada rodada, apenas um participante treina, recebendo o modelo do participante anterior e passando o modelo atualizado para o próximo. Após todos os participantes passarem pelo modelo, inicia-se uma nova rodada com o primeiro participante:

\begin{equation}
w^{(t+1)} = w_{i_t}^{(t+1)}, \quad \text{onde}\; i_t = t \bmod N
\end{equation}

Cada participante acrescenta suas árvores ao modelo existente sem sobrescrever o que os outros aprenderam. Para modelos de boosting, essa abordagem permite um refinamento incremental e controlado, especialmente quando combinada com redução gradual da taxa de aprendizado nas rodadas posteriores \cite{li2020practical}.


\subsection{Modelos Baseados em Árvore de Decisão}

Os algoritmos de boosting baseados em árvore são o estado da arte para dados em formato de tabela \cite{liu2024survey}. Eles combinam centenas de árvores de decisão pequenas adicionadas sequencialmente, onde cada nova árvore é treinada para corrigir os erros das anteriores. Ao contrário de redes neurais profundas, esses modelos são mais eficientes computacionalmente, mais resistentes à reconstrução de dados a partir das atualizações transmitidas \cite{zhu2019deepleakage}, e naturalmente adequados para o ambiente federado \cite{cheng2021secureboost, li2023fedtree}.

Uma árvore de decisão faz predições dividindo os dados em regiões com base em condições sobre as características. Para uma amostra $x$, a predição do modelo completo após $K$ árvores é simplesmente a soma das contribuições de cada árvore:

\begin{equation}
\hat{y}(x) = \sum_{k=1}^{K} f_k(x)
\end{equation}

onde $f_k(x)$ é a predição da $k$-ésima árvore. O objetivo do treinamento é minimizar uma função de perda que penaliza tanto os erros de predição quanto a complexidade excessiva do modelo (para evitar sobreajuste, ou \textit{overfitting}):

\begin{equation}
\mathcal{L} = \sum_{i=1}^{n} \ell(\hat{y}_i, y_i) + \sum_{k=1}^{K} \Omega(f_k)
\end{equation}

onde $\ell$ mede o erro de predição e $\Omega(f_k)$ penaliza modelos muito complexos.


\subsubsection{XGBoost}

XGBoost (\textit{eXtreme Gradient Boosting}) \cite{chen2016xgboost} é um dos algoritmos mais populares para dados tabulares. Sua principal inovação em relação a implementações anteriores é o uso de uma aproximação matemática de segunda ordem (expansão de Taylor) para calcular com mais precisão o quanto cada nova árvore deve contribuir, e um forte sistema de regularização que penaliza modelos muito complexos. O XGBoost inclui suporte nativo a valores ausentes, treinamento em GPU e regularização L1 e L2. A sua adaptação para o ambiente federado foi formalizada pelo SecureBoost \cite{cheng2021secureboost}.


\subsubsection{LightGBM}

LightGBM (\textit{Light Gradient Boosting Machine}) \cite{ke2017lightgbm} é um algoritmo desenvolvido pela Microsoft com foco em velocidade e uso eficiente de memória. Sua principal diferença é a estratégia de crescimento das árvores: enquanto a maioria dos algoritmos divide todos os nós do mesmo nível antes de descer (\textit{level-wise}), o LightGBM sempre divide o nó que produz a maior redução de erro, mesmo que isso gere árvores assimétricas (\textit{leaf-wise}). Essa abordagem converge mais rápido na maioria dos problemas.

Para reduzir ainda mais o custo computacional, o LightGBM usa duas técnicas: a primeira reduz o número de amostras usadas no cálculo dos ganhos, mantendo apenas as amostras com maiores erros e descartando parte das com erros pequenos (amostragem baseada em gradiente, ou \textit{GOSS}); a segunda agrupa características que raramente assumem valores não-nulos ao mesmo tempo, reduzindo a dimensionalidade sem perder informação (empacotamento exclusivo de características, ou \textit{EFB}). A manutenção da eficiência do LightGBM em ambientes federados foi demonstrada por Li, Wen e He \cite{li2020practical}.


\subsubsection{CatBoost}

CatBoost (\textit{Categorical Boosting}) \cite{prokhorenkova2018catboost} é um algoritmo desenvolvido pela Yandex que se diferencia por duas características principais. A primeira é o tratamento nativo de características categóricas (como tipo de emprego ou sistema operacional) sem necessidade de pré-processamento extensivo: o algoritmo calcula estatísticas internas baseadas no valor-alvo para codificá-las automaticamente, evitando que informação do conjunto de teste "vaze" para o treinamento (\textit{data leakage}). A segunda é o treinamento ordenado (\textit{ordered boosting}): para eliminar um viés sistemático presente em outros algoritmos de boosting, o CatBoost calcula o gradiente de cada amostra usando apenas as amostras anteriores a ela em uma ordenação aleatória. O CatBoost usa árvores simétricas, onde a mesma condição de divisão se aplica a todos os nós do mesmo nível, o que funciona como regularização natural e acelera a predição.

O CatBoost não foi avaliado no artigo original do BAF \cite{jesus2022baf}, tornando sua inclusão neste trabalho uma contribuição inédita.


\subsection{Framework Flower}

Flower \cite{flower2020} é um sistema de código aberto para Aprendizado Federado independente do algoritmo de aprendizado de máquina utilizado. Ele funciona com PyTorch, TensorFlow, alguns algoritmos da biblioteca Scikit-Learn, uma versão adaptada do XGBoost, além de outros tipos de algoritmos. Foi escolhido para este trabalho por ser o principal framework de Aprendizado Federado atualmente disponível, ademais, oferece implementações nativas das estratégias Bagging e Cíclica para modelos de boosting e por permitir simular múltiplos participantes em uma única máquina sem precisar de infraestrutura de rede real.

\begin{figure}[H]
\centering
\includegraphics[width=0.60\textwidth]{figures/flower-any.jpeg}
\caption{Arquitetura do Flower: sistema de código aberto que suporta diferentes tipos de participantes e algoritmos de aprendizado de máquina. Fonte: \cite{flower2024whatisfl}}
\label{fig:flower_architecture_fund}
\end{figure}

A arquitetura do Flower, ilustrada na Figura \ref{fig:flower_architecture_fund}, é organizada em três componentes que trabalham juntos em cada rodada de treinamento.

O ponto de partida é o \textbf{Participante} (\textit{Client}). É ele que possui os dados e, por isso, é quem realiza o aprendizado propriamente dito. No Flower, o participante implementa dois métodos obrigatórios: \texttt{fit()}, que recebe o modelo global, o treina com os dados locais e devolve o modelo atualizado; e \texttt{evaluate()}, que avalia o desempenho do modelo nos dados locais sem modificá-lo. Tudo o que acontece dentro do participante --- os dados, o processo de treinamento, os resultados intermediários --- permanece invisível para o restante do sistema.

Quem coordena todo o processo é o \textbf{Servidor} (\textit{Server}). Em cada rodada $t$, o servidor seleciona os participantes $\mathcal{S}_t$ que vão contribuir, distribui o modelo global $w^{(t)}$ para cada um deles, aguarda o retorno dos modelos atualizados $\{w_i^{(t+1)}\}_{i \in \mathcal{S}_t}$ e produz o novo modelo global $w^{(t+1)}$. Esse ciclo se repete por $T$ rodadas até que o modelo atinja o desempenho desejado. O servidor, no entanto, não decide \emph{como} combinar os modelos --- essa responsabilidade pertence ao terceiro componente.

A \textbf{Estratégia} (\textit{Strategy}) define a lógica de combinação dos modelos e a política de seleção dos participantes. Sua separação do servidor é uma das decisões de projeto mais importantes do Flower: permite trocar o algoritmo de combinação --- Bagging, Cíclica, média ponderada (\textit{FedAvg}) \cite{mcmahan2017fedavg}, entre outros --- sem modificar uma linha sequer do código do servidor ou dos participantes. Para experimentos como este trabalho, essa modularidade é essencial: é possível comparar estratégias completamente diferentes mantendo todo o restante do sistema idêntico.

A comunicação entre os componentes usa transmissão estruturada de dados (\textit{Protocol Buffers}) sobre chamadas remotas de procedimento (\textit{gRPC}), transmitindo os parâmetros dos modelos como sequências de bytes. Esse formato garante compatibilidade independentemente do algoritmo utilizado internamente.

O Flower opera em dois modos. O \textbf{modo de simulação} executa todos os participantes em um único processo, usando o sistema Ray para distribuir os cálculos entre núcleos locais --- este é o modo utilizado neste trabalho. O \textbf{modo de implantação} executa participantes e servidor em máquinas separadas, comunicando-se pela rede real, sendo o modo adequado para sistemas em produção com instituições geograficamente distribuídas.

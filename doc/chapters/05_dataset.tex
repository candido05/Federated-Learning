\section{DATASET E PREPARAÇÃO DOS DADOS}

\subsection{A Escolha do Dataset}

Um dos primeiros obstáculos práticos deste trabalho foi encontrar dados adequados para treinar e avaliar modelos de detecção de fraude em um ambiente federado. Dados reais de transações bancárias são extremamente sensíveis: os bancos não os compartilham publicamente, e qualquer conjunto de dados disponível precisaria garantir que nenhuma informação de clientes reais pudesse ser identificada ou reconstruída. A maioria dos conjuntos de dados públicos sobre fraude financeira é pequena, desatualizada ou não foi projetada especificamente para o cenário de abertura de contas.

Foi nesse contexto que se identificou o \textit{Bank Account Fraud} (BAF) \cite{jesus2022baf}, publicado em 2022 na conferência NeurIPS (\textit{Track on Datasets and Benchmarks}). O BAF foi criado pelo laboratório de pesquisa da Feedzai, uma empresa portuguesa de tecnologia financeira, e se tornou o primeiro conjunto de dados público de grande porte criado especificamente para detectar fraudes em abertura de contas bancárias online, com privacidade garantida por construção. Ele foi criado gerando dados sintéticos a partir de dados bancários reais anonimizados, usando um tipo de rede neural gerativa chamada CTGAN \cite{xu2019ctgan} --- em termos simples, um modelo de inteligência artificial treinado para aprender os padrões estatísticos dos dados reais e gerar novos registros que se comportam de forma similar, mas que não correspondem a nenhuma pessoa real. Antes da geração, ruído estatístico foi adicionado aos dados originais para garantir uma camada adicional de privacidade, e após a geração foi verificado que nenhum registro sintético coincidia exatamente com um registro real. O resultado é um conjunto de aproximadamente um milhão de aplicações de contas bancárias, com 30 características por registro, cobrindo oito meses de operação.

\subsection{O Que os Dados Representam}

Cada linha do dataset BAF representa uma única solicitação de abertura de conta bancária feita por uma pessoa em uma plataforma online. A coluna-alvo é \texttt{fraud\_bool}: o valor 1 indica que aquela solicitação foi identificada como fraudulenta (por exemplo, alguém usando identidade roubada ou falsa para abrir uma conta e depois usá-la para esgotar o crédito ou receber pagamentos ilícitos), e o valor 0 indica uma solicitação legítima.

Este cenário tem uma característica importante do ponto de vista social: na União Europeia, ter acesso a uma conta bancária é considerado um direito básico. Isso significa que rejeitar uma solicitação legítima --- o chamado falso positivo --- não é apenas um problema técnico, mas pode impedir uma pessoa real de acessar serviços financeiros essenciais. É por isso que o dataset e este trabalho dão atenção especial não apenas à taxa de detecção de fraudes, mas também à equidade do modelo para diferentes grupos de pessoas.

As 30 características do dataset cobrem quatro tipos de informação. O primeiro é o perfil do solicitante: faixa etária, nível de renda, situação de emprego e moradia. O segundo são dados da própria solicitação: tipo de pagamento escolhido, valor de crédito proposto, canal de acesso e sistema operacional do dispositivo utilizado. O terceiro são verificações automáticas: se o e-mail é de um provedor gratuito, se os telefones informados são válidos, se a solicitação veio de um endereço estrangeiro. O quarto são métricas de atividade recente: quantas solicitações ocorreram com o mesmo código postal nas últimas quatro semanas, quantos e-mails distintos foram usados no mesmo dispositivo nas últimas oito semanas, quantas tentativas de fraude já foram detectadas naquele dispositivo. Esta última categoria é especialmente valiosa porque fraudadores frequentemente testam múltiplas identidades no mesmo dispositivo ou endereço antes de uma tentativa bem-sucedida.

\subsection{O Desafio do Desbalanceamento}

Ao explorar o dataset, o primeiro ponto que chama atenção é a proporção entre fraudes e solicitações legítimas: apenas cerca de 1\% das solicitações são fraudulentas. Isso significa que, para cada fraude, há aproximadamente 99 solicitações legítimas --- e essa proporção muda ligeiramente ao longo dos meses, chegando a 1,47\% no mês mais recente (mês 7).

Este desbalanceamento extremo cria um problema sério para qualquer modelo de aprendizado de máquina: se o modelo simplesmente classificar tudo como legítimo, ele acerta em quase 99\% dos casos, mas não detecta nenhuma fraude. Por isso, a acurácia simples não serve como métrica de avaliação aqui. Seguindo a recomendação dos autores do BAF \cite{jesus2022baf} --- que reflete o que sistemas reais em produção utilizam --- adotou-se como métrica principal o TPR (\textit{True Positive Rate}, ou taxa de fraudes corretamente detectadas) no ponto em que o modelo produz no máximo 5\% de FPR (\textit{False Positive Rate}, ou taxa de solicitações legítimas incorretamente rejeitadas). Em outras palavras: dado que se aceita rejeitar erroneamente no máximo 5 de cada 100 clientes legítimos, quantas fraudes é possível detectar? Quanto maior esse valor, melhor o modelo.

Para lidar com o desbalanceamento durante o treinamento, todos os algoritmos receberam um parâmetro que atribui mais peso às amostras de fraude na hora de aprender. Para os dados de treino usados nos experimentos, a razão entre amostras legítimas e fraudulentas resultou em um fator de peso de 96,53 --- o modelo "penaliza" mais quando erra uma fraude do que quando erra uma solicitação legítima.

\subsection{Preparação dos Dados}

Os dados brutos do BAF passaram por uma sequência de transformações antes de serem usados nos experimentos. Esse processo foi construído gradualmente, à medida que se explorava o dataset e se identificava o que precisava ser corrigido ou enriquecido.

O primeiro passo foi a limpeza. O dataset usa o valor $-1$ para indicar que uma informação estava ausente --- por exemplo, o tempo no endereço anterior de quem não tem endereço anterior. Esses valores foram substituídos por um marcador adequado de dado ausente e preenchidos com a mediana de cada coluna calculada apenas nos dados de treino. Três colunas foram removidas por serem pouco informativas ou por terem problemas de qualidade (\texttt{prev\_address\_months\_count}, \texttt{intended\_balcon\_amount} e \texttt{device\_fraud\_count}), e a coluna \texttt{velocity\_24h} foi removida por ter correlação muito alta com as outras colunas de velocidade, o que tende a confundir os modelos. Ao final dessa etapa, um pequeno número de registros com dados críticos ausentes foi descartado.

O segundo passo foi a criação de novas características (\textit{feature engineering}), ou seja, calcular informações derivadas dos dados originais que os modelos possam explorar mais diretamente. Entre as novas características criadas estão: razões entre velocidades em janelas de tempo diferentes (por exemplo, quantas solicitações houve nas últimas 6 horas comparado com as últimas 4 semanas, o que sinaliza picos de atividade suspeita), Z-scores mensais para normalizar as métricas de velocidade em relação ao comportamento médio daquele mês, uma combinação de faixa etária com nível de renda, e uma variável binária indicando se o solicitante tem 50 anos ou mais, usada na análise de equidade. No total, essa etapa expandiu o conjunto de 30 características originais para 99 características.

O terceiro passo foi a codificação das características categóricas, como tipo de pagamento, situação de emprego, sistema operacional do dispositivo e outras. Para que os modelos possam trabalhar com elas numericamente, cada valor distinto de uma categoria se torna uma coluna binária --- técnica chamada de \textit{One-Hot Encoding}. Esse processo foi ajustado exclusivamente nos dados de treino e depois aplicado igualmente aos dados de validação e teste, evitando que informação dos dados de teste "vaze" para o processo de treinamento.

\subsection{A Divisão Temporal dos Dados}

O BAF organiza os dados em oito meses consecutivos (identificados como meses 0 a 7). Essa estrutura temporal é importante: ao contrário de uma divisão aleatória, ela simula como um modelo seria realmente usado em produção --- treinado nos dados mais antigos e avaliado nos dados mais recentes, que refletem padrões que ainda não existiam quando o modelo foi treinado. Fraudadores adaptam suas táticas ao longo do tempo, então um modelo que funciona bem nos dados do mês 3 precisa generalizar para os padrões do mês 7.

A divisão adotada foi: os meses 0 a 5 (os seis primeiros) formam o conjunto de treino, com 794.680 registros; o mês 6 forma o conjunto de validação, com 108.132 registros, usado durante o treinamento para acompanhar o desempenho do modelo a cada rodada; e o mês 7 forma o conjunto de teste final, com 96.829 registros, que só foi consultado ao final de cada experimento para medir o resultado definitivo. O artigo original do BAF utiliza apenas dois conjuntos (treino e teste), e a criação de um conjunto de validação separado foi uma extensão necessária para calibrar os limiares de decisão durante o treinamento federado sem contaminar a avaliação final.

As taxas de fraude crescem ligeiramente ao longo do tempo: 1,03\% no treino, 1,34\% na validação e 1,47\% no teste. Essa variação é esperada em dados reais e afeta o ponto de operação a 5\% FPR quando o limiar é recalibrado em cada conjunto --- razão pela qual os valores de TPR medidos na validação (durante o treinamento) são sistematicamente diferentes dos medidos no teste (avaliação final).

\subsection{A Divisão para o Aprendizado Federado}

O Aprendizado Federado exige que os dados de treino sejam divididos entre os clientes participantes, de forma que cada cliente tenha apenas sua própria fatia dos dados e nunca acesse os dados dos outros. Neste trabalho, os dados de treino foram divididos de forma equilibrada entre 3 clientes: cada um recebeu 264.893 registros, com 2.716 casos de fraude (taxa de 1,03\%), mantendo a mesma proporção de fraudes do conjunto original. Esse tipo de divisão --- onde todos os clientes têm dados com distribuição estatística similar --- é chamado de particionamento IID (\textit{Independent and Identically Distributed}), e foi escolhido para isolar o efeito das estratégias de agregação sem que diferenças nos dados de cada cliente influenciassem os resultados.

Os conjuntos de validação e teste não foram divididos: eles ficaram no servidor central e foram usados exclusivamente para avaliar o modelo global após cada rodada de treinamento e ao final dos experimentos.

\subsection{As Variantes do BAF e a Escolha pelo Dataset Base}

O BAF disponibiliza seis versões do mesmo dataset: um \textit{Base} e cinco variantes que introduzem tipos diferentes de desequilíbrio nos dados para testar a robustez dos modelos. As variantes alteram a proporção entre grupos demográficos (\textit{Variante I}), a taxa de fraude por grupo (\textit{Variantes II e IV}) ou a facilidade de classificar fraudes em grupos diferentes (\textit{Variantes III e V}). Esses desequilíbrios controlados permitem avaliar se um modelo aprende de forma injusta, penalizando certos grupos mais do que outros.

Neste trabalho, foi utilizado o dataset \textbf{Base}, que é a versão mais próxima das características do dataset original sem desequilíbrios artificiais adicionados. Ele já apresenta uma leve disparidade natural entre grupos: o grupo majoritário (77\% das solicitações) tem taxa de fraude de 0,9\%, enquanto o grupo minoritário (23\% das solicitações) tem taxa de 1,8\%. Essa assimetria existente no dataset Base é suficiente para tornar a análise de equidade relevante, sem introduzir vieses artificialmente extremos.

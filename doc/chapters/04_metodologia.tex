\section{METODOLOGIA}

\subsection{Visão Geral da Solução}

Este trabalho propõe um sistema de Aprendizado Federado para detecção de fraudes bancárias usando modelos baseados em árvore. A ideia central é que cada participante (representando uma instituição financeira ou filial) mantém seus dados localmente e colabora no treinamento de um modelo global por meio do framework Flower \cite{flower2020}. Ao final, todos os participantes se beneficiam de um modelo treinado sobre dados mais diversos, sem que nenhum deles precise compartilhar informações sensíveis dos seus clientes \cite{yang2019fl, kennedy2025financial}.

A escolha por XGBoost \cite{chen2016xgboost}, LightGBM \cite{ke2017lightgbm} e CatBoost \cite{prokhorenkova2018catboost} em vez de redes neurais profundas é sustentada por três razões documentadas na literatura. Primeiro, modelos de boosting podem atingir precisão comparável ao treinamento centralizado em dados federados enquanto preservam a privacidade, conforme demonstrado pelo SecureBoost \cite{cheng2021secureboost}. Segundo, eles são ordens de magnitude mais eficientes do ponto de vista computacional do que redes neurais, o que é crítico para detecção de fraude em tempo real \cite{li2023fedtree}. Terceiro, ao transmitir informações sobre divisões e histogramas em vez de gradientes brutos, eles são naturalmente mais resistentes a ataques de reconstrução de dados do que redes neurais \cite{liu2024survey, zhu2019deepleakage}.

O sistema avalia duas estratégias de combinação de modelos --- Bagging e Cíclica --- para identificar qual abordagem produz os melhores resultados no domínio de detecção de fraudes em abertura de contas bancárias, usando o dataset BAF \cite{jesus2022baf} como base experimental.

\subsection{Arquitetura do Sistema}

A arquitetura segue o modelo cliente-servidor do Aprendizado Federado Horizontal \cite{yang2019fl}, cenário em que todos os participantes coletam o mesmo tipo de dados (solicitações de abertura de conta) sobre pessoas diferentes. O servidor central coordena o treinamento: inicializa o modelo global, seleciona participantes para cada rodada, distribui os parâmetros do modelo, combina as atualizações recebidas e avalia o modelo global usando um conjunto de validação centralizado \cite{bonawitz2019scale}.

Cada cliente representa um participante do sistema com uma fatia local do dataset BAF, simulando diferentes instituições bancárias colaborando sem compartilhar dados. Os dados são divididos em particionamento IID equilibrado: todos os clientes recebem aproximadamente o mesmo número de amostras com a mesma distribuição de fraudes. Essa escolha permite isolar o efeito das estratégias de combinação sem que diferenças nos dados de cada cliente influenciem os resultados --- o foco principal do trabalho. Cenários com dados heterogêneos entre participantes são apontados como direção para trabalhos futuros \cite{zhu2021noniid, li2020fedprox}. A comunicação entre clientes e servidor é gerenciada pelo Flower, que cuida de toda a parte de transmissão e sincronização dos modelos \cite{flower2020}.

\subsection{Divisão dos Dados entre Participantes}

Os dados de treino são divididos de forma equilibrada entre os clientes. As amostras de cada classe (fraude e legítima) são separadas, embaralhadas e distribuídas igualmente, garantindo que cada participante receba a mesma proporção de fraudes do conjunto original. Assim, todos os clientes têm aproximadamente a mesma taxa de fraude que o dataset global, sem nenhum desvio que pudesse interferir na comparação entre algoritmos.

\subsection{Implementação dos Modelos Federados}

Cada algoritmo (XGBoost, LightGBM e CatBoost) foi implementado como um cliente Flower, seguindo a interface padrão do framework \cite{flower2020}. Todos os três compartilham a mesma estrutura com dois métodos obrigatórios:

\begin{itemize}
    \item \texttt{fit(ins: FitIns) -> FitRes}: Realiza o treinamento local usando os dados do cliente e retorna o modelo atualizado. A partir da segunda rodada, o treinamento começa a partir do modelo global recebido, acumulando conhecimento progressivamente.

    \item \texttt{evaluate(ins: EvaluateIns) -> EvaluateRes}: Avalia o modelo global nos dados locais do cliente, retornando métricas de desempenho para acompanhamento pelo servidor.
\end{itemize}

A transmissão dos modelos entre clientes e servidor requer convertê-los para sequências de bytes. Cada algoritmo tem uma forma diferente de fazer isso: o XGBoost serializa diretamente em formato JSON via \texttt{save\_raw()}; o LightGBM e o CatBoost exigem gravação em arquivos temporários. Para unificar o processo, todos os modelos são convertidos e transmitidos como sequências de bytes (arrays NumPy), garantindo compatibilidade com o protocolo do Flower.

O treinamento incremental --- ou \textit{warm start} --- é suportado pelos três algoritmos. A partir da segunda rodada, o treinamento não começa do zero, mas continua a partir do modelo global recebido do servidor, preservando o que foi aprendido nas rodadas anteriores \cite{konecny2016communication}.

\subsection{Estratégias de Combinação de Modelos}

Para os três algoritmos, foram implementadas estratégias personalizadas que herdam da classe \texttt{Strategy} do Flower, dando controle completo sobre como os modelos locais são combinados.

\textbf{Estratégia Bagging}: Todos os clientes treinam em paralelo a partir do mesmo ponto de partida. Na primeira rodada, cada cliente treina do zero; nas rodadas seguintes, o servidor seleciona o melhor modelo da rodada anterior (baseado no TPR de validação) e o envia para todos os clientes como ponto de partida. Ao final de cada rodada, cada cliente retorna seu modelo atualizado, e o servidor mantém o melhor deles para a próxima rodada. A predição do modelo global é feita pela média das probabilidades calculadas por cada modelo local.

\textbf{Estratégia Cíclica}: Os clientes treinam sequencialmente em ordem circular. O modelo percorre os clientes um a um --- cada cliente acrescenta suas árvores ao modelo recebido e passa o resultado para o próximo. Um ciclo completo (todos os clientes treinando uma vez) equivale a uma rodada de aprendizado colaborativo.

\subsection{Métricas de Avaliação}

As métricas principais são calculadas ao final de cada rodada no conjunto de validação e, ao fim do experimento, no conjunto de teste:

\begin{itemize}
    \item \textbf{TPR @ 5\% FPR}: Taxa de fraudes detectadas no ponto de operação em que a taxa de falsos positivos é exatamente 5\%, conforme a métrica de referência do BAF \cite{jesus2022baf}.
    \item \textbf{AUC-ROC}: Área sob a curva ROC, que mede a capacidade de discriminação do modelo independentemente do limiar de decisão escolhido.
    \item \textbf{FPR Ratio}: Razão entre as taxas de falso positivo dos dois grupos demográficos ($\min/\max$). Valores próximos a 1,0 indicam que os dois grupos são tratados de forma igualitária.
    \item \textbf{Tempo de execução}: Duração total da simulação, em segundos.
    \item \textbf{Dados transferidos}: Volume total de dados transmitidos entre clientes e servidor ao longo de todas as rodadas.
\end{itemize}

Os resultados são avaliados em dois regimes de limiar, conforme definido no artigo do BAF \cite{jesus2022baf}. No regime \textbf{standard}, um único limiar global é calibrado para que a taxa de falsos positivos no conjunto completo seja exatamente 5\%. No regime \textbf{fair}, dois limiares independentes são calibrados separadamente: um para o grupo com idade $\geq 50$ e outro para o grupo com idade $< 50$, cada um ajustado para 5\% de FPR no respectivo grupo. Esse ajuste equaliza as taxas de falso positivo entre os dois grupos sem modificar o modelo treinado \cite{hardt2016equality}.

\subsection{Limitações Metodológicas}

É importante reconhecer as limitações desta abordagem. O particionamento equilibrado entre clientes não captura a heterogeneidade presente em cenários reais onde diferentes instituições têm perfis distintos de clientes \cite{zhu2021noniid}. A simulação também não replica completamente os desafios de sistemas em produção em escala, como latência variável, falhas de comunicação e participantes mal-intencionados \cite{miao2022byzantine}. Por fim, o sistema não implementa técnicas adicionais de privacidade como Combinação Segura \cite{bonawitz2017secagg} ou Privacidade Diferencial \cite{geyer2017differential}, focando exclusivamente na avaliação de desempenho e equidade dos algoritmos.
